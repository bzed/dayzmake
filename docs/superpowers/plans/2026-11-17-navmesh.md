# DayZ navmesh generation, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `dayzmake-core` gains a navmesh generator. It fetches a world's geometry from DayZDiag's navmesh data
server (or from a capture file), builds every tile with a DayZ-patched Recast/Detour port and writes the game's
`.nm` file. The CLI exposes it as `dayzmake navmesh probe|generate|info`, and the MCP server as `navmesh_probe`,
`navmesh_generate` and `navmesh_info`.

**Architecture:** This is a new module `dayzmake_core::navmesh` behind a new additive feature `navmesh` (on by default).
It has four layers, each a submodule:
- `wire` + `client` + `capture`: the data-server protocol, TCP and `.dzgeo` captures;
- `recast`: the voxel pipeline, ported from upstream Recast with the DayZ changes of spec §10.1, plus `dayz` (the DayZ
  passes of spec §5);
- `detour`: tile creation, the tiled mesh with linking, the queries the island filter needs and the `.nm` set file;
- `build` (one tile) and `generate` (the scheduler).
The CLI and MCP layers are thin wrappers in the root crate.

**Tech Stack:** Rust 1.99, edition 2024, std only (`std::net`, `std::thread::scope`, `std::sync::mpsc`). There are no
new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-17-navmesh-cleanroom-spec.md` (written as the clean-room functional spec of
Flare Navgen 0.3.0). In the tasks, "§n" refers to its sections. The spec is binding for behaviour, constants, byte
layouts and formulas; this plan's **dayzmake rulings** below override it where they differ.

  `TESM` set, and has no generator. It is used as a layout reference.

## dayzmake rulings (override or settle the spec)

1. **Deterministic output.** The assembler adds finished tiles to the mesh in **plan order** (§8.4), not in
   completion order. It keeps a reorder buffer keyed by plan index, so output is byte-identical for any `threads` and
   `connections`. This is a deliberate difference from §8.4's completion order (AGENTS.md: same input, same output).
2. **Scope of commands.** dayzmake implements `probe`, `generate` (with `--capture`/`--record`) and `info`. It does not
   implement `capture`, `capture-info`, `replay-server`, `tile`, `roundtrip`, `export-obj`, `render`, `diff`,
   `verify`, `merge`, `resave` or `islands`. Ctrl+C handling is left out too: resuming is `--checkpoint` plus
   `--base <out> --skip-existing`.
3. **Ports.** Hosts are `host` or `host:port`, and the default port is 36533. Tests use a fake server on
   `127.0.0.1:0`.
4. **Retry.** The rules of §3.6 apply, but the delays come from `RetryPolicy { attempts: 5, delay_unit:
   Duration::from_secs(2) }`, so the delay is `delay_unit * (attempt + 1)`. Tests pass `delay_unit: ZERO`. The receive
   timeout is 600 s by default, and tests pass a shorter one.
5. **Limits beyond the spec (hostile input).** The spec's limits (§12.1) stay. On top of those:
   - `cells <= 2048` per cell class ("implausible cell count");
   - nothing is allocated from a count before that count times its element size has been checked against the bytes
     left in the payload;
   - the frame cap stays 1 GiB, but the client reads a frame into a `Vec` growing in chunks of at most 16 MiB, never
     `with_capacity(length)`.
6. **`RSQRTSS`.** On `x86_64`, use `std::arch::x86_64::{_mm_set_ss, _mm_rsqrt_ss, _mm_cvtss_f32}`. With Rust 1.99
   and SSE in the x86_64 baseline these are safe to call. If the compiler demands `unsafe`, stop and report
   `BLOCKED`, because `unsafe_code` is forbidden. Other architectures use `1.0 / d.sqrt()`; rustdoc and the book say
   that the output there can differ from DayZ's in slope classification.
7. **BV tree sort.** Sort with `sort_by` (stable) on the axis key, then the polygon index. This is a valid tree, but
   it can differ from MSVC `qsort` tie order (open question 3). This is documented as a known difference.
8. **Ladders.** Ladders get direction value 1, as in §6.1 (the literal behaviour). The reverse merge follows the
   literal logic of §6.4.
9. **Errors and warnings.**
   - Library functions return `std::io::Error` (`error!`, `prepend_error`).
   - Failed tiles do not abort the run. They are returned in `GenerateReport::failed` (`Vec<(i32, i32, String)>`).
   - New warnings go through the `WarningSink`:
     - `navmesh-stray-part`: one per tile that had stray part ids, see §12.3;
     - `navmesh-seed`: the island filter found no polygon near the seed;
     - `navmesh-tile-failed`: one per failed tile, besides the report.
   - The CLI exits 1 when `failed` is non-empty, after the file has been saved.
10. **Progress.** `generate` takes `progress: &mut dyn FnMut(&Progress)`. It is called after each finished tile and
    once at the end. The library never prints.
11. **Atomic writes** (§9.6). The `.nm` is written to a temp file in the target's directory and renamed. There is no
    delete-then-rename.

## Review Focus

1. **Thread count changes the output.** `threads 1` versus `threads 4` with `connections 2` must give identical
   bytes; Task 13 tests this.
2. **Hostile server or capture.** Huge counts, truncated payloads, part ranges out of bounds, NaN vertices, a
   mismatched tile answer and frames longer than announced must return errors, never panic or allocate
   unboundedly. Tasks 1 and 2 test this, plus the fuzz targets.
3. **Ranges at the world edge.** A range with negative coordinates, beyond the grid or inverted is clamped (§8.4).
   An inverted range gives zero tiles and an error "empty tile range", not a panic. Task 13 tests this.
4. **Resume equals a full run.** A run stopped after a checkpoint (simulated by a range), then
   `--base out --skip-existing` over the full range, must give the same bytes as one full run. Task 13 tests this.
5. **The data server is not there.** `navmesh probe` against a closed port fails within the connect timeout. The
   error names `host:port` and says "start DayZDiag_x64.exe with -server -startNavmeshDataServer". An existing
   target without `--force` writes nothing. Task 14 tests both.
