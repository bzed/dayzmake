**Spec:** the GitHub issues #37–#41, #43, #45, #53, #54 and #57 on bzed/dayzmake (read with `gh issue view N -R bzed/dayzmake`).

## Global Constraints

## Review Focus

- A stdout that is a terminal, a pipe or `/dev/null` must not be treated as an own-output file (#38).
- BrokenPipe on stderr (not stdout) still fails normally (#39).

---

### Task 1: Own-output exclusion on case-insensitive file systems (#37)

Compare by file identity (device + inode on unix, volume + file index on Windows; check for a reviewed crate first,
e.g. `same-file`) instead of by name. Windows CI test of the issue's repro. Commit `fix: never pack the own output on case-insensitive file systems (#37)`.

### Task 2: stdout redirected into the source folder (#38)

When stdout is a regular file, exclude its identity like a file target. Test: the issue's repro → no `out.pbo` entry.
Commit `fix: pack and build never pack a redirected stdout (#38)`.

### Task 3: Closed stdout pipe (#39)

Handle `ErrorKind::BrokenPipe` on stdout once in `main`/`run`: exit quietly with status 0, no error line (README
`## Changes`). Test as in the issue. Commit `fix: a closed stdout pipe ends the command quietly (#39)`.

### Task 4: Device-name targets that are regular files (#40)

`src/cli_io.rs` device shortcut (Windows): after the direct open, if `file.metadata()` reports a regular file, fall
back to the checked temp-file path (respects `--force`, truncates). Windows CI test as in the issue. Commit
`fix: a regular file with a device-like name is not overwritten in place (#40)`.

### Task 5: Warning wording (#41)

Emit `leading-separator` only when the entry is actually extracted; the #35 replace warning names the stored entry.
Also the items in the #41 comment (generated entry name stored in `generated_names` and printed; the loop calls the `entry_name` helper instead of duplicating the rename; cross-platform pin with a plain ODOL `m.p3d` next to `m.p3do`). Tests as in the issue. Commit `fix: unpack and build warnings name what actually happens (#41)`.

### Task 6: A closed stderr pipe panics (#43)

Every CLI write to stderr (errors in `main`/`run`, `src/cli_warnings.rs`, any other `eprintln!`) uses `writeln!(io::stderr(), …)`
and ignores a failed write, with a comment saying why; the exit status stays what the command decided. Tests as in the
issue (spawn with stderr a pipe whose read end is closed). Commit `fix: a closed stderr pipe no longer panics (#43)`.

Also in Task 6 (Task 3 review minors): the `closed_stdout_pipe_ends_inspect_quietly` fixture grows to about 2000
entries so its output always exceeds the pipe buffer; a `#[cfg(unix)]` test that a BrokenPipe on a FIFO file target
still fails with exit 1.

### Task 7: Include cycles and include depth (#53)

`preprocess_rec` (`crates/dayzmake-core/src/preprocess.rs`, ~795): an include of a file already on `info.import_stack`
is an error naming the chain (paths through `printable`); nesting deeper than a limit (32, one documented constant) is
an error. Tests (files under a TempDir): self-include, A→B→A, a linear chain of 33. Also give the `config_parse` fuzz
target a way to exercise includes without host files (an in-memory include resolver if the API has one, otherwise
document why it stays skipped). Commit `fix: include cycles and deep include chains are errors (#53)`.

### Task 8: Nesting limits in the grammars (#54)

One documented nesting limit (e.g. 512) for the preprocessor grammar's `arg_rec`, config class nesting, array nesting
and `__EVAL` parentheses (`crates/dayzmake-core/src/preprocess.rs`, `config.rs`, `eval.rs`); deeper input is a parse
error, never a stack overflow — check that the limit holds on a 1 MiB thread stack in a debug build (run the parser in
a thread with that stack size in the test). Tests: each repro of #54 generated in the test; a realistic config still
parses. Fuzz seeds with moderately deep nesting. Commit `fix: config and preprocessor nesting has a limit (#54)`.

### Task 9: Exponential macro expansion (#57)

A cap on the expanded output per line and per file (tokens or bytes; generous for real configs — check every
`config.cpp`/`*.hpp` under `~/workspace/dayz` read-only before and after, output must stay byte-identical, as in the
#51 review) and an error naming the macro (through `printable`) when it is exceeded. Test: the #57 repro with N=30
fails fast (under a second in a debug build); a CBA-style macro set still expands. Fuzz seed with N=20. Commit
`fix: macro expansion output is capped (#57)`.
