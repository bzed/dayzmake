disagree with it, the files win, and the implementer corrects the spec document in the same commit.

### Task 1: Config enums (#82)

**Files:** `crates/dayzmake-core/src/config.rs` (parser, `Config`, rapified writer and reader); tests in
`crates/dayzmake-core/tests/` (the existing config test file); `docs/book/src/reference/` page for
rapify/derapify; READMEs.

- [ ] Tests first (all FAIL before the change):
  - `rapify_enum_block`: the source `enum { A, B = 5, C };\nclass X { y = 1; };`. In the output, `enum_offset`
    points to `u32 3` followed by `"a\0" 0`, `"b\0" 5`, `"c\0" 6` (names lowercase, source order). Class `X`
    is unchanged compared with the same source without the enum.
  - An enum inside a class is accepted and lands in the same global table.
  - `derapify_enum_table`: a hand-built `.bin` with a two-value table. The text output starts with
    `enum {` … `};` listing `name = value`.
  - Round trip: derapify → rapify → derapify gives identical text.
  - A table offset past the end of the file, or a table cut short, is no error: you get the values read so far,
    or none.
  - A hostile count (`0xFFFF_FFFF` with no data) neither allocates nor panics.
- [ ] Implement:
  - Parse `enum { name [= int], ... };` (optional trailing comma).
  - Values count up from the last explicit one, as in C.
  - Store them in `Config` as an ordered `Vec` with a public accessor (for example
    `pub fn enum_values(&self) -> &[(String, i32)]`, or a small `#[non_exhaustive]` struct).
  - The rapified writer writes the table at `enum_offset` (it writes an empty table today: check this).
  - The reader reads it.
  - Derapify prints the block first.
- [ ] Manual check with no commit: derapify all 801 files in `/var/tmp/cfgbin.8GvUI0/`. All succeed, and the 735
  with tables print an enum block. Then rapify each derapified text again and compare its enum table entries
  (as a set) with the original. Report the numbers.
- [ ] `cargo test --locked --workspace`: PASS, no snapshot changes.
- [ ] Commit `feat: config enum blocks are rapified and derapified (#82)`, with `Fixes #82` in the body.

### Task 2: PAA RGBA4444, ARGB1555, AI88 and the PNG error (#83)

**Files:** `crates/dayzmake-core/src/paa.rs`. LZSS: there is a private `lzss_decompress` in
`crates/dayzmake-core/src/pbo.rs`. Move it to a shared private module (for example
`crates/dayzmake-core/src/lzss.rs`, `pub(crate)`), extended so it returns how many input bytes it consumed;
PBO behaviour stays unchanged. Tests go in `crates/dayzmake-core/tests/paa_api.rs`; also the docs for
`paa2img` and `paa_to_image`, and the READMEs.

- [ ] Tests first (FAIL before the change):
  - One hand-built 4×4 PAA per type (`0x4444`, `0x1555`, `0x8080`): one LZSS mipmap with literal bytes only,
    plus a correct signed checksum. `to_dynamic_image` gives the expected RGBA pixels: the bit layouts are in
    #83.
  - A wrong checksum is an error.
  - A truncated stream is an error.
  - A file starting with the PNG signature: the error message says it's a PNG file.
  - The existing tests for unsupported formats need updating; keep the test for a truly unknown magic.
- [ ] Implement decoding to RGBA, within the existing `MAX_PAA_TOTAL` budget. The expected size is
  `width*height*2`, computed with checked arithmetic. Writing these formats is not required: `write` on a `Paa`
  read from such a file should either round-trip the stored bytes or fail clearly. Check what `write` does today
  for stored data and keep that working.
- [ ] Manual check with no commit, under `prlimit`: decode the 19 game textures of these types and report each
  result (path, size, OK or error). Find them with `scan.py`. Also report whether any of them sets the LZO bit.
  If the checksum or bit layouts disagree with #83, the files win; report the difference.
- [ ] `cargo test --locked --workspace`: PASS, snapshots unchanged.
- [ ] Commit `feat: PAA reads RGBA4444, ARGB1555 and AI88 (#83)`, with `Fixes #83`.

### Task 3: ODOL v56 reader in dayzmake-core (#84, library part)

**Files:** a new `crates/dayzmake-core/src/odol.rs` (public module, documented), `lib.rs`; tests in
`crates/dayzmake-core/tests/odol.rs`; a fuzz target `fuzz/fuzz_targets/odol.rs` with seeds in the corpus layout
of the other targets; the seeds also go into `crates/dayzmake-core/tests/fuzz_seeds.rs`. Update
`docs/superpowers/specs/2026-11-16-odol-v56-layout.md` where the files disagree with it.

- [ ] Read the spec document fully first.
- [ ] LZO: the stream length isn't stored, so the decoder must report the input bytes it consumed. Check whether
  `lzo1x` 0.2.2 (already used for PAA) can do that, for example by an error or return value that shows the
  consumed length, or by decoding from a slice and reporting the position. If it can't, review a crate per
  AGENTS.md (source review; the result goes into the commit message). Writing a small, bounded LZO1X
  decompressor ourselves is allowed only if no crate passes; then say why in the commit message.
- [ ] Public API (all types `#[non_exhaustive]`, ordered `Vec`s):
  - `Odol::read(&mut (impl Read + Seek)) -> Result<Odol, Error>`. It fails clearly for a version other than 56
    ("ODOL version N is not supported, only 56").
  - `Odol` has: `version`, model-level `property_class`, `property_damage`, skeleton name and bone count,
    animation class names and sources, and `lods: Vec<OdolLod>`.
  - `OdolLod` has: `resolution: f32`, `name()` (reusing `p3d::lod_name` and MLOD's naming), `vertex_count`,
    `face_count`, `textures: Vec<String>`, `materials: Vec<OdolMaterial>` (name + stage texture paths),
    `proxies: Vec<String>` (model paths), `selections: Vec<String>`, `properties: Vec<(String, String)>`.
- [ ] Tests first: build a minimal synthetic ODOL v56 by hand in the test, with a test helper that writes the
  layout: 2 LODs, one with a proxy, 2 textures, a material with one stage, a section, a named selection, a
  property; the second LOD has a compressed array of 1024 bytes or more. Assert every field. Then the hostile
  cases:
  - truncated at every byte boundary of the header: an error, never a panic (loop over the prefixes);
  - `lod_count` `0xFFFF_FFFF`;
  - a LOD start past the end;
  - a string with no NUL;
  - an LZO stream that overruns its declared size.
- [ ] Implement following the spec, with the limits from its *Limits* section.
- [ ] Manual check with no commit, under `prlimit`: parse every `.p3d` in the three game roots. Extract to a
  `/var/tmp` dir or read the entries in place; adapt `scan.py` or write a small `--example`/test binary that is
  not committed. Report: files OK out of the total, the distinct material versions seen, the first 5 failures
  with LOD index and offset. Target: 100% OK. If the spec is wrong somewhere, fix the reader **and the spec
  document**.
- [ ] Fuzz target plus 3–5 small synthetic seeds; `make fuzz` (10 s per target) for the new target, under
  `prlimit`.
- [ ] `cargo test --locked --workspace`, `make lint`, `make doc`: PASS.
- [ ] Commit `feat: read ODOL v56 models (#84)` (no `Fixes`: that comes in Task 4).
