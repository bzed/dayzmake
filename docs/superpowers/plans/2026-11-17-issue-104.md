### Task 1b: 64-bit integer entries and wide hex literals (#106)

Added while Task 1 ran. CfgConvert writes `x = 2147483648;` as entry subtype 6 (int64), and dayzmake's reader rejects
that subtype. `0x1FFFFFFFFF` gives `-1` in CfgConvert and an error in dayzmake.

**Files:** `crates/dayzmake-core/src/config.rs` (the `ConfigEntry`/`ConfigArrayElement` types, the rapified reader
and writer, the integer grammar actions, derapify output); `tests/fixtures/bi/cfgconvert/` and its README; tests in
`crates/dayzmake-core/tests/` (`config.rs`, `bi_golden.rs`); the fuzz seeds if the reader gains a branch.

- [ ] Reference run with CfgConvert (Task 1's setup). Inputs:
  - entries `a = 2147483647; b = 2147483648; c = -2147483649; d = 9223372036854775807; e = 9223372036854775808;`
  - `f = 0xFFFFFFFF; g = 0x100000000; h = 0x1FFFFFFFFF;`
  - the same values as array elements: `arr[] = {2147483648, 0x1FFFFFFFFF, 9223372036854775808};`

  Record the entry subtype and the element type bytes, and the decoded values. Add the input and CfgConvert's `.bin`
  as fixtures, with a golden test.
- [ ] Ruling: follow CfgConvert byte for byte, for both the type and the value:
  - Reading subtype 6 must work: new variant `ConfigEntry::Int64Entry(i64)`. The enum is `#[non_exhaustive]`, so this
    is additive. Add the matching array element variant only if CfgConvert writes one.
  - Rapify picks the subtype CfgConvert picks.
  - Derapify writes an integer literal that reads back to the same subtype, so derapify followed by rapify
    round-trips bit for bit.
  - Task 1 made a decimal that doesn't fit i64 a float (`1e20`). Keep that, and make it consistent with the int64
    range: i32 → subtype 2, then i64 → subtype 6, then float.
  - Hex literals do what CfgConvert does.
- [ ] Hostile input: the reader checks the length before it reads 8 bytes, with no panic. Add a fuzz seed with
  subtype 6, plus a truncated one.
- [ ] Every place that matches on `ConfigEntry` handles the new variant: `api config` display and JSON, `eval`, and
  `binarize`. Search for the existing `IntEntry` arms.
- [ ] Changes bullets in both READMEs (new public variant), and the book's config page. PASS, then `make lint`.
  Commit `fix: read and write 64-bit integer config entries like CfgConvert`, with `Fixes #106`.

### Task 1c: enum values like CfgConvert (#107)

Added while Task 1b ran. CfgConvert passes enum values through f32:
- `A = 2147483647`, `2147483648`, `4294967296`, `99999999999999999999` and `-2147483649` all give `-2147483648`, and
  so does the next implicit name;
- `A = 16777217, B` gives 16777216 twice;
- wide hex wraps (`0x1FFFFFFFFF` → -1), and `0X10` works.

dayzmake errors on all of these. The recorded rows are in `tests/fixtures/bi/README.md`.

**Files:** `crates/dayzmake-core/src/config.rs` (the enum grammar and the enum value and next-value logic); tests in
`crates/dayzmake-core/tests/config.rs` and `bi_golden.rs`; `tests/fixtures/bi/cfgconvert/`.

- [ ] Ruling: follow CfgConvert. An enum value is computed as CfgConvert does: hex wraps to 32 bits, decimals go
  through f32 and then saturate to i32 the way the observed results show. The implicit next value is the previous
  f32 value + 1, computed in f32 and then converted.
- [ ] If the recorded rows don't decide a case (for example `-0x10` versus a float, or a value between 2^24 and
  2^31), run CfgConvert once more (same setup and limits) and record the result.
- [ ] Tests first: a golden built from the recorded CfgConvert inputs. Update the existing enum tests that expect
  `Invalid integer` for wide values, keeping each test's purpose (test another error path if one is left). They
  FAIL first.
- [ ] `__EVAL` of large numbers: keep dayzmake's exact floats. CfgConvert's imprecise low bits are not copied.
  State this in the bi README and close that part of #107 in the commit body.
- [ ] Changes bullets in both READMEs, and the book's config page. PASS, then `make lint`. Commit
  `fix: enum values follow CfgConvert's f32 semantics`, with `Fixes #107`.

### Task 6b: download verification rejects expired keys and signatures (#109)

Added on request. `gpg --verify` prints `Good signature` and exits with 0 for a signature from a key that has expired
since. Both the README check and `sign-release.sh`'s check accept it.

**Files:** `README.md` (section *Verifying downloads*, between the `ANCHOR: verifying` markers; the book includes it),
`scripts/sign-release.sh` (`verify_all`), `scripts/test-sign-release.sh`, and the `AGENTS.md` lines about the signing
key if they describe the check.

- [ ] Docs, Linux and macOS:
  - Replace the bare `gpg --verify` line with a check of the status output. It passes only if there is a
    `[GNUPG:] GOODSIG ` line **and** a `[GNUPG:] VALIDSIG 662441B36A5785AD18FB8667DF753D99D064EB7E ` line (the
    primary key signs; there is no subkey), and then prints `signature OK`. For example:
    `s=$(gpg --status-fd 1 --verify SHA256SUMS.asc SHA256SUMS 2>/dev/null)`, followed by both `grep -q`s and
    `echo 'signature OK'`.
  - Explain in one or two sentences that the `Good signature` text is not enough: gpg prints it for an expired key
    too, and only `GOODSIG` means the signature and key are valid and not expired or revoked.
- [ ] Docs, Windows (PowerShell with Gpg4win): the same check with `Select-String` on
  `gpg --status-fd 1 --verify … 2>$null`. It must print `True` only when both lines are present.
- [ ] `sign-release.sh` `verify_all`: verify each `.asc` with `--status-fd` and require GOODSIG plus VALIDSIG of the
  fingerprint of the published key (read it from the imported key with `--with-colons`, not hard-coded), in a
  shell function that the test can call.
- [ ] `test-sign-release.sh`, tests first:
  - a signature made with `--faked-system-time` while a 1-day key was valid, verified now, after the key expired,
    must be rejected by the new check;
  - a good signature still passes;
  - a signature by a different valid key is rejected (wrong VALIDSIG).

  Run `scripts/test-sign-release.sh` (throwaway keys, no secrets). Run the real docs commands once against a real
  release (`gh release download v3.0.2 -R bzed/dayzmake -p 'SHA*' -p 'dayzmake-release-key.asc'` into a
  `mktemp -d /var/tmp/…` dir, deleted afterwards) to show they print `signature OK`.
- [ ] Commit `fix: download verification rejects expired keys and signatures`, with `Fixes #109`.
