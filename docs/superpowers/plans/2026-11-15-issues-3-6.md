# Fixes for Issues #3–#6, #8 and #9 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the four CLI oddities found while recording the characterization snapshots: lost `delete` in
derapify (#3), inconsistent warning paths in `build` (#4), open errors without the file name (#5), and a
misleading `unpack` conflict message (#6), writing a read PBO corrupting its LZSS-compressed entries (#8), and a parser panic on non-ASCII leading whitespace (#9).

**Architecture:** Six independent fixes, one task and one commit each. Each fix changes the characterization
snapshots that pin the old behaviour, deliberately, and names them in the commit.

**Tech Stack:** Rust 1.99, `insta` snapshots, the dayzmake workspace (`dayzmake-core` + `dayzmake`).

**Spec:** GitHub issues https://github.com/bzed/dayzmake/issues/3, /4, /5, /6, /8 and /9. The
issue text is binding where this plan is silent.

## Global Constraints

- The workspace split is merged (PR #7, `653954e`). Branch `fix/issues-3-6` from `main`. Paths below are the post-split layout: core in
  `crates/dayzmake-core/src/`, CLI helpers in `src/commands/*.rs` and `src/cli_io.rs`. If a name differs, follow the
  code and say so in the report.
- All `AGENTS.md` rules apply. `make check` passes after every task.
- Snapshot changes: only the snapshots each task names, only in the way it names; review every `.snap.new` by hand.
  The commit body lists each changed snapshot.
- Untrusted names (PBO entry names, paths from files) printed in messages go through `dayzmake_core::error::printable`.
- Commit subjects end with `(#N)`; the body has `Fixes #N` and ends with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- CLI behaviour change → README updated in the same commit if it documents the old message (search README for the
  old text).

## Review Focus

1. A top-level `delete X;` (outside any class) must survive rapify → derapify too, not only nested ones (Task 1).
2. `build` run from a different cwd (`dayzmake build mod out.pbo`) and warnings raised **inside an included file**
   must also come out addon-relative, not as `mod/…` or as an absolute canonicalised path (Task 2).
3. An include that lives outside the addon (found through `-i`) keeps its path as today: it cannot be made
   addon-relative and must not be mangled (Task 2).
4. File names with control characters in open errors and unpack conflicts are escaped (`printable`), never written
   raw to the terminal (Tasks 3, 4).
5. `unpack` with a conflict must write nothing, and `--force` must still overwrite everything (Task 4).
6. A read PBO written back unchanged must stay readable with identical entry contents, and its signature (made after
   writing) must verify (Task 5).
7. Any text config, whatever its whitespace or encoding, gives an error and never a panic (Task 6, plus a fuzz target).

**Interfaces:**
- `pbo::unpack` (from the split plan) checks every target path (all entries that pass the filters and

### Task 5: Writing a read PBO keeps its compressed entries intact (#8)

**Files:**
- Modify: `crates/dayzmake-core/src/pbo.rs` (`write_with_checksum`, `file_data`, the entry-header lookup)
- Test: `crates/dayzmake-core/tests/pbo_api.rs` (hand-built PBOs via `tests/support/mod.rs::raw_pbo`; extend the
  helper to take a packing method and original size per entry if it cannot yet)

**Interfaces:**
- No public API change. Behaviour:
  - `write` of an entry whose stored header (from `PBO::read`) has packing method `Cprs` (`PACKING_COMPRESSED`) and
    that was not replaced since (`insert_entry` drops the header of the name it touches): write that header's
    `packing_method` and `original_size` with `data_size` = stored length. `timestamp` and `reserved` stay `0` as for
    every written entry (deterministic output). All other entries are written as today.
  - Duplicate entry names in a read PBO: `files` keeps the **last** value (`LinkedHashMap::insert` semantics, at the
    position of the first). `file_data` and `write` must use the header that belongs to that value: the last header
    with that name (`rposition`/`rfind`), not the first.
